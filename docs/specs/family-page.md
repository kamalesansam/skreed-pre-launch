**Decision (Sam, 2026-10-09): the case only.** No phone, device body, glass or lens parts are ever drawn inside or behind the case. The camera window shows whatever is behind the case (the page neutral). This overrides every mention of a Device part, device glass or the device contrast check below.

## 1. Goal

Let a visitor see all 24 shades of one family as real cases side by side, pick one, read its name and number, choose Matte or Gloss, and carry that shade to Reserve.

Brand goals served (00-IDEATION section 1): **1** (a lifestyle brand built on colour: the family is the product), **2** ("this changes everything": 24 real shades of one hue on one case is the colour system made visible), **3** (the page ends in "Reserve my shade" with the shade carried over).

## 2. Phone-first wireframe in words

### 2.1 Routes

- One static page per family, generated by Astro at build: `src/pages/shades/[family].astro`, `getStaticPaths()` over `families` in `docs/data/shades-240.json`. The slug is the family `id` (already the slugified display name). Ten URLs, served as `/shades/{slug}/`:
  `/shades/frosty-whites/`, `/shades/blissful-blues/`, `/shades/playful-pinks/`, `/shades/vivid-violets/`, `/shades/mellow-yellows/`, `/shades/earthy-browns/`, `/shades/blushing-corals/`, `/shades/stormy-greys/`, `/shades/go-green/`, `/shades/roaring-reds/`.
- The build fails if there are not exactly 10 families, if any family has other than 24 shades, if a shade name repeats inside a family, or if a family `id` is not URL-safe. (Names do repeat across families: Pastel 6 times, Neon 4, Royal, Indigo, Classic, Teal, Stone, Midnight, Orchid, Wine and Persian twice; identity is always family plus index.)
- **Shade number.** Derived, never stored: `catalog number = (family ordinal - 1) x 24 + index`, 1 to 240, shown with three digits ("032 / 240"), the same format section 2's labels use. A family's numbers are contiguous, so `<html data-first="025">` (set at build) is all a page needs to validate one.
- **Selected shade in the URL:** `/shades/blissful-blues/?shade=032`. The query value is the three-digit catalog number, the same key the reserve link uses. Selection changes rewrite it with `history.replaceState` (debounced 300 ms), so a copied URL opens the same shade and Back leaves the page instead of stepping through shades.
- Unknown slug: the site 404 (G1). Nothing else is generated: no per-shade pages (section 8).
- Page data is inlined at build: the family's 24 shades (id, index, name, hex, catalog number), the ten families' names, slugs and key shades for the switcher, and the case model manifest (imported into the island chunk). No runtime fetch of `shades-240.json` or of the manifest.
- **Shade colours under the CSP.** The site CSP fails the build on any markup `style` attribute (`hero-architecture.md` 12.3). So no hex is written into markup. A generated stylesheet (`src/styles/shades.gen.css`, from `shades-240.json`) defines the 240 shades as tokens on `:root` (`--shade-001` to `--shade-240`, as CLAUDE.md asks), and each page adds one rule per shade it shows (its 24 plus the 10 key shades): `[data-s="032"] { --sw: var(--shade-032); }`. Every swatch (scrubber, grid, switcher, sticky bar) is an element with `data-s="NNN"` and `background: var(--sw)`. Runtime changes go through CSSOM (`el.style.setProperty('--shade', ...)`), which the CSP allows.

**Key shade per family.** The shade each section 2 rock holds, taken from the hero (`prototypes/hero-v9/template.html`, `REGION`, one shade per family in catalog order). It is the page's default selection and the family's swatch in the switcher. It moves into one shared data file at build (`src/data/family-keys.json`) that section 2 and the family pages both import, so the two can never disagree.

### 2.2 Entry from the section 2 rocks (integration contract for the hero owner)

**Mapping.** A rock's family is the family of the shade it holds. In the hero each block `b` carries `b.shade`, an index into `REGION`, which is in catalog family order; so `families[b.shade]` is the rock's family and its link is `/shades/{families[b.shade].id}/?shade={key shade catalog number}`. The link is derived from that index at runtime, never from a second hand-written table, so a different block colour order (`?blockColors=warm`, `wheel`, `original`) cannot break a link. With today's default "cool" order the ten blocks are:

**Pointer and touch (one rule).** Hover keeps section 2's existing behaviour (labels, frost, cursor `pointer` over a rock). Navigation listens to the native `click` event on the canvas and acts only when `event.target` is the canvas itself and the pointer moved 10 px or less since `pointerdown`, with no time limit, so a slow, deliberate tap counts and a drag stays a scroll. A click on any DOM control or label never reaches it, which removes ciao's click-through defect (study section 12 item 5: ciao's raycast listens on `window`). Section 2's tap splat may play; navigation is never delayed for it. This replaces section 2's "tap a rock = splat plus labels" (labels already follow the scroll window on phones).

**Keyboard and assistive technology.** Ten real links in a `<nav id="families" aria-label="Colour families">` holding an `<ol>`, in **catalog order** (Frosty Whites first), whatever the rocks' screen order. Each is `<a href="/shades/{slug}/?shade={NNN}">` with the accessible name "Blissful Blues, all 24 shades".
- They are always in the accessibility tree and the tab order. The only exception is the hero's own rule that everything behind the loader is `inert` while the loader shows (hero D16).
- In the 3D path each link's box is positioned over its rock's projected bounding box every frame the labels update (the labels' own projection), at least 44 x 44 px, transparent at rest, with `pointer-events: none`. The boxes serve the keyboard and screen readers only; the canvas raycast owns pointer input, so hover labels and frost keep working and the event-target rule above holds.
- On `focus`, if section 2 is not at its rest position, the page scrolls instantly (`behavior: 'auto'`) to section 2's rest scroll position from the hero's `SCROLL_MAP`, then shows the site focus ring around the rock's box and makes it the focus rock (labels, smoke, plexus as the hero spec defines). Enter follows the link.
- On the poster path (no WebGL2, data saver, low memory, reduced motion under the default tier) the same ten links are drawn visibly as section 2's fallback grid (ten circle swatches captioned "Sky, Blissful Blues, 032 / 240"), so there is one set of ten links in every mode. The existing Reserve link stays beside the grid.

**A route that needs no 3D.** The Wall (section 3) links each family tab or caption to `/shades/{slug}/` (contract for the Wall spec; `family_open` with `from: 'wall'`). Section 2's links and the Wall's are the two ways in from the landing; the family switcher links the ten pages to each other.

**Prefetch.** When a rock is hovered for 150 ms or its link focused, insert `<link rel="prefetch" href="/shades/{slug}/">` once per family. The model is not fetched on the landing.

**Hand-off.** Cross-document view transitions, scoped (R14): the landing opts in with `@view-transition { navigation: auto; }` and a `pageswap` handler that calls `event.viewTransition.skipTransition()` unless the destination path starts with `/shades/`, so the landing's other links (privacy, terms) navigate plainly. The family pages opt in for links among themselves and back to `/`. The browser's default 0.25 s root cross-fade where supported, a plain navigation elsewhere, `navigation: none` under reduced motion. No camera fly-in before navigating; ciao's 1.5 s page turn (study section 6) would delay the next page.

**Return path.** "Tap a rock, look, go back, tap another" is this feature's main loop.
- Before following a rock link, the landing runs `history.replaceState(null, '', '#families')`, so the history entry it leaves is `/#families`.
- On landing load, when `performance.getEntriesByType('navigation')[0].type` is `'back_forward'` or the hash is `#families`, the hero skips its loader (its `skip` path) and does not run `scrollTo(0, 0)` (D16 already skips it when a hash is present). The browser restores the scroll position, so the visitor is back on section 2 with the rocks live.
- On `pageshow` with `persisted` true (back-forward cache), the hero checks `gl.isContextLost()` and rebuilds through its restore path if the context is gone (iOS can return a cached page with a lost context), then resumes its loop.

**Analytics.** PostHog `family_open` with `{family, from: 'rock' | 'rock_grid' | 'switcher' | 'family_nav' | 'wall'}`.

**On tap, swipe, scroll.**
- Tap a visible case: it becomes the selection. The line slides so it comes to the centre, in one move, however far away it was.
- Tap the front case: it turns 10 degrees toward the side you tapped and back over 600 ms, so its finish reads (a matte surface rolls its shading, a gloss highlight crosses the back). Nothing else happens; it never navigates or scrolls.
- Swipe horizontally on the stage: the line follows the finger 1:1 (44 px per shade). On release it settles on the nearest case, with a fling (velocity carried for 0.2 s). Past the first or last shade the line resists (35% of the finger travel) and springs back. Vertical swipes scroll the page (`touch-action: pan-y`).

- Matte / Gloss: the finish changes on all 24 cases at once, and the front case plays the same 600 ms turn.
- Every selection change: the name line swaps (one 400 ms move, old and new together), family and number update in the same move, the scrubber's selected swatch moves, the sticky bar's swatch cross-fades over 600 ms.
- Scroll down: below the stage the page continues (2.6). Nothing reveals on scroll; everything is visible at rest (D1).

**Units and coordinates.** The CaseModel normalises the case so its height is 1.0 (case-model-class.md). w is the case width and d its thickness in those units, read from the model's bounding box (the stand-in: w 0.472, d 0.075, from 77 x 163 x 12.3 mm). World axes are three's: +X to the viewer's right, +Y up, +Z toward the camera. Rotations are right-handed: a positive yaw (about +Y) turns a case's back toward +X; a positive lean (about the case's own +Z, its back normal) turns it counter-clockwise as the viewer sees it, top to the left.

**Pose function.** For slot i (0 to 23, catalog order), eased selection s and promotion G (0 in the poster pose, 1 live; it rises with the entrance):
- x = i - s, p = G x max(0, 1 - abs(x)), c = clamp(x, -1, 1).
- Position: X = x x pitch + c x gap x G; Y = 0 (a level line); Z = lift x p - G x 0.1 x min(abs(x), 3).
- Rotation, applied lean first (in the case's own plane), then yaw: lean = 3 degrees x p; yaw = -fan x c x (1 - p) + (-15 degrees) x p. Scale = 1 + (S - 1) x p.
- Constants: fan 62 degrees, S 1.4, lift 0.3, pitch = 0.9 x (w cos fan + d sin fan) (0.2596 for the stand-in, so each case overlaps the next like books), gap = 0.5 x (S x (w cos 15 + d sin 15) + (w cos fan + d sin fan)) - pitch + 0.02 (0.2377 for the stand-in), which keeps the front case clear of its neighbours for any model shape. T5 (case-model-class.md) confirms the clearance with oriented boxes; the builder tunes against the screen targets of section 7, not by eye alone.
- Two cases can be partly promoted during a move; p is continuous, so nothing pops.

**Camera.** Perspective, vertical FOV 20 degrees, looking at the front slot's centre (the world origin) from distance D: from 4 degrees below the line (looking up) and 4 degrees to its left (looking right), then rolled about its own view axis by -8 degrees (`camera.lookAt(0, 0, 0)` then `camera.rotateZ(-8 degrees)`), so the level line rises 8 degrees to the right on screen. Fixed during interaction; re-solved on every stage resize (ResizeObserver on the stage box, width or height).
- **Scale by layout class** (px per world unit at the origin). Phone layout: 170 px per unit, constant at every width, so a strip is 44.1 px; reduced only when the case column would not fit the stage height minus 24 px (landscape phones, 2.8). Wide layout: D solved so the front case is 0.385 x the stage height, clamped to 240 to 340 px.
- **Vertical framing** with `camera.setViewOffset`, solved over every selection from 01 to 24 in half steps: on the phone layout the case column is centred in the stage; on the wide layout the lowest case pixel sits 16 px above the HUD band (the bottom 224 px of the stage). Both are relative to the stage box, never absolute page y.

**Lighting and environment.** `scene.environment` from a PMREM of three's RoomEnvironment (blur 0.04; procedural, 0 bytes downloaded, 1.2 KB gzip of code), `scene.environmentIntensity` E and one white directional key at (-2, 3, 4) with intensity K, physical units. After the PMREM is made, the PMREMGenerator and the RoomEnvironment scene are disposed (case-model-class.md 11). E and K start at 1.0 and 1.0 and are then set by calibration B, never by eye. No shadows, no fog, no HDR file, no spotlights, no gobo. Tone mapping Neutral at exposure 1.0, output sRGB. Canvas transparent (alpha, clear alpha 0) over the flat page neutral, so the same lighting reads on Pearl and on Slate pages.

**Post-processing.** None. No EffectComposer, so ciao's DPR-squared pass sizing cannot happen. Anti-aliasing is MSAA on the default framebuffer (`antialias: true`). No bloom (rule 42); the gloss highlight comes from the environment and the key.

**Selection model.** One store: `target` (integer, or fractional while a finger is down), `s` (eased) and `G` (eased promotion). The HUD, scrubber, sticky bar, live region and URL follow `round(target)`, updated at most every 150 ms while a finger is down and at once for discrete input. One `selection` event `{index, previous, input}` per settled change, which the DOM and analytics listen to.

**Inputs.** Pointer Events on the canvas for every pointer type.
- Tap or click: the native `click`, accepted only when `event.target` is the canvas, the pointer moved 10 px or less since `pointerdown`, and no drag ended in the last 100 ms. It raycasts the instanced meshes (the front-most hit wins). A hit on another case selects it; a hit on the front case plays the turn.
- Drag: the axis locks after 6 px. Horizontal moves the line 1:1 with the pointer; vertical is left to the page (`touch-action: pan-y`). Fling on release: target = round(s - v x 0.2 s / strip width in px), with v the pointer velocity averaged over the last 80 ms (dragging left moves the line left, toward higher shades).
- Prev and Next, the scrubber (pointer and keys), the grid in 2.6. The canvas is `aria-hidden` and not focusable; the keyboard path is the scrubber and the grid.
- Hover (fine pointers): one pick per animation frame at most, for the cursor only.

**Idle.** Nothing moves. After the selection settles (abs(target - s) under 0.0005, G at 1, tilt settled, any turn done) the loop renders two more frames and stops. It restarts on input, resize, context restore or the pointer entering the stage. It also stops while the stage is off screen (IntersectionObserver) or the tab is hidden.

**Pointer tilt.** The front case's back turns toward a fine pointer over the stage, up to 5 degrees of yaw and 3 of tilt, times p, at the lineup's rate, and eases back to rest when the pointer leaves. It is new motion on these pages (R5), off on coarse pointers and under reduced motion.

**Tiers.** The head gate (2.7) decides 3D or swatch grid mode before first paint with the hero's D3 signals. Inside the 3D path a probe sets the tier once the model and the PMREM are ready:
- Before rendering, 10 animation frames with no rendering give the display's frame period P (the minimum interval seen; 16.7 ms at 60 Hz, 8.3 ms at 120 Hz, 33.3 ms in iOS Low Power Mode).
- Then 20 forced renders of the scene. Where `EXT_disjoint_timer_query_webgl2` exists, the GPU time of each is read; otherwise the rAF interval is used.
- High tier when the median render costs 1.25 P or less (GPU time 0.75 P or less with the timer query). Otherwise low tier: DPR 1, the front case stays at LOD1, gloss without clearcoat; then the probe runs once more, and a median above 3 P (50 ms at 60 Hz) sends the page to swatch grid mode.
- LOD0 is fetched only after a high-tier verdict, so a low-tier phone never downloads it. Never fewer than 24 cases.

### 2.7 Swatch grid mode (no 3D)

## 4. Motion plan

No GSAP on these pages (decision 10): every DOM move is a CSS transition or the Web Animations API, and the 3D runs in the page's own frame loop. Reduced motion has one source, `src/scripts/motion.ts`, the module the hero uses (hero D6), plus CSS media queries. The durations and curves below are registered in `DESIGN.md` section 10 before the build (R13).

| What | Library | Trigger | Move | Reduced motion (the 3D rows apply only under `still3d`; by default reduced motion is grid mode, where the DOM rows apply) |
|---|---|---|---|---|
| The lineup | three.js, own loop | Selection, drag, resize | Exponential approach at 10.94 per second, frame-rate independent (63, 210, 421 ms); drag 1:1; fling; rubber band 35% | `s` jumps to `target`; no fling, no rubber band |
| Entrance converge | Own loop | First live frame | G 0 to 1 and s from the poster pose to the selection at the same rate; any input retargets | None: the first frame is the selection |
| Poster to canvas | CSS | First live frame ready | Canvas opacity 0 to 1 over 200 ms on top of the poster (`--dur-canvas`) | Instant |
| Front-case tilt | Own loop | Fine pointer over the stage | Up to 5 degrees of yaw and 3 of tilt toward the pointer, at the lineup's rate, back to rest on leave | Off |
| Front-case turn | Own loop | Matte or Gloss pressed; tap or click on the front case | Yaw 10 degrees toward the tapped side (to the right for a finish press) and back, 600 ms, `--ease-turn` cubic-bezier(0.45, 0, 0.55, 1) | Off; the material swaps |
| Name and number swap | Web Animations API | Settled or discrete selection change | Inside an overflow mask, old line to translateY(-110%) and new line from 110% to 0, both at once, 400 ms (`--dur-swap`), `--ease-swap` cubic-bezier(0.25, 1, 0.5, 1) (the CSS form of power3.out); never an empty slot; a new swap finishes the running one at its end state first | Instant text change |
| Scrubber selected swatch | CSS transition on transform | Selection | Moves to its slot, 400 ms, `--ease-swap` | Instant |
| The sticky-bar swatch | Web Animations API, opacity only (amended in review iteration 2, C3) | Selection | The swatch takes the new shade at once; a copy of the old shade on top fades out over 600 ms (`--dur-shade`), so no colour is animated; a newer copy goes under the ones still fading | Instant, no copy |
| Buttons | CSS | Hover, press | Hover `translateY(-1px)`, press `scale(0.98)`, 150 ms `--ease-standard` (type-system note 7); no opacity change | Colour change only |
| Rock to family page, family to family, back to `/` | CSS view transitions, scoped (2.2) | Navigation | Browser default root cross-fade | `navigation: none` |

No Lenis, no ScrollTrigger, no scroll-linked motion, no sound.

## 9. Decisions taken

1. **The line has ends, no wrap.** Catalog order has a first and a last shade; ciao's wrap also caused its centre-index and long-way defects.
2. **ciao's conveyor on every screen.** The selected case is always the centred slot and the line slides under it, with no clamp at the ends, so the name always reads directly under the front case. v1's still laptop line is dropped. The laptop still shows all 24 for mid-family selections (10 to 14 at 1280) and never fewer than 14.
3. **A fanned row (62 degrees, overlapping like a swatch deck) instead of ciao's twisted can diagonal.** A flat case turned 100 degrees per slot would show its edge or its inside; turned toward the front case every back stays visible.
4. **Drag on every pointer type.** With the conveyor, dragging is the direct input everywhere (v1's "no drag on laptop" reversed); drag direction and click selection agree on every screen.
5. **The front case is drawn at LOD0, the row at LOD1** (case-model-class.md); the switch happens one slot from the front, where both look the same.
6. **Shade number shown as "032 / 240"** in Open Sans 600 tabular, the format of section 2's labels; "#212" stays the reservation position of type-system role 10c, so a shade number and a queue number can never be confused.
7. **Key shade = the rock's shade**, also the switcher swatch.
8. **Stage neutral per family**, alternating Slate and Pearl in catalog order, flat, for the whole page.
9. **Reduced motion follows the hero.** v1's "keep the 3D, motionless" rested on a false premise: hero D2 and DESIGN.md give reduced motion the poster path, with still-3D behind `REDUCED_MOTION_TIER` for Sam. These pages read the same flag and gates (2.7, R11).
10. **No GSAP, no Lenis, no ScrollTrigger, an instant switcher, no countdown, no sound** on these pages. Two DOM moves (name swap, scrubber marker) do not justify 28 KB or more against a 250 KB cap that PostHog and the beacon also draw on.
11. **Prev at 01 and Next at 24 are disabled** rather than turning into family links; family navigation lives in its own row.
12. **No camera fly-in on the way in.** The rock click navigates at once; the view transition cross-fade is the hand-off.
13. **Neutral tone mapping, RoomEnvironment, no post-processing.** From the colour test and to avoid ciao's composer defect.
14. **One global colour calibration**, never per-shade corrections (case-model-class.md).
15. **The stand-in case never ships.** The production build fails if the model manifest names the stand-in. A `FAMILY_3D=off` build mode omits the island, the manifest and the posters, so the pages can launch in swatch grid mode if Sam asks for that before the model arrives.
16. **Model compression: meshopt with the pure-JavaScript decoder (amended 2026-10-09, replaces "quantisation only").** The user's Cobalt model, optimised to the analysis quality bar (LOD0 20,348 triangles for the close-up, LOD1 9,811 for the lineup), ships as `EXT_meshopt_compression` + `KHR_mesh_quantization`: LOD0 106,000 B raw (76,771 B Brotli), LOD1 54,688 B raw (39,033 B Brotli). Quantisation only would cost 310,396 B and 137,944 B raw, or a cut to about 10k and 4.2k triangles, under the close-up bar. The page decodes with meshoptimizer's pure-JS `meshopt_decoder_reference.js` (0.22.0, 1,398 B Brotli), which compiles no WebAssembly and loaded both files under the site CSP with zero violations; LOD1 decodes identically to the WASM decoder, LOD0 differs in 14 of 153,500 normal values by 1 LSB; decode 6 to 40 ms measured. The site CSP is unchanged (no `'wasm-unsafe-eval'`). Upstream labels the reference decoder unoptimised for speed, so T16 adds a decode-time budget (LOD1 under 50 ms on the mid-phone trace). Draco and Basis stay out. A Cloudflare Compression Rule for `.glb` (`model/gltf-binary` is not compressed by default) is part of the first deploy.
17. **A selection-neutral poster and a short converge** replace ciao's 4.5 s entrance: the poster never contradicts a deep link, and the live line settles in 421 ms (99%) without locking input.
18. **Even lighting on all 24 cases.** ciao lights only its centred can; here every case must match its swatch.
19. **Phone scale 170 px per world unit.** It makes each strip 44.1 px, so tapping a strip meets the tap-target rule without an exception, and keeps two full neighbours a side from 360 to 430 px wide. v1's 151 gave 39 px strips.
20. **A tap on the front case turns it** (600 ms) instead of opening anything: the closest honest equivalent of ciao's "open the product" without a per-shade page.
21. **Swatch colours through generated tokens and `data-s` attributes**, never `style` attributes, because the CSP build check fails on them; runtime colour changes go through CSSOM.
22. **Deep-link state on `<html>` from a head script**, selected markers in CSS, text behind same-box skeletons until the module writes it.
23. **The poster download is accepted in swatch grid mode**, including data saver: the preload scanner fetches it before any script can read `saveData`, and `prefers-reduced-data` ships in no browser. Serving the HTML through a Worker that drops the poster on `Save-Data` would add a Worker to a static route for at most 80 KB.
