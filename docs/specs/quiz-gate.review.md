### Verdict: FAIL

1. **The ride's wait for the hall does not wait (AC4, D3, H Loading, H Slow network, F1).** `window.__skreedHall.load()` is `loadHall()` (`hero.ts` 233, 221), which ends in the hall's own `load()`, and that returns at once once its load has started (`async load() { if (started) return; started = true; ... }`, `src/scripts/hero/section4/hall.ts` 156 and 157). The hall's load has always started before the ride races it: the stage observer calls `loadHall()` as soon as the quiz comes into view (amendment 1, `hero.ts` 308), and `unlock('skip')` dispatches `skreed:quiz-unlock`, whose listener calls `loadHall()` (`hero.ts` 230) before `ride()` runs. So whenever `hall.ready` is false at the press, `Promise.race([hall.load(), wait(HALL_WAIT_MS)])` (`gate.ts` 124) settles a few microtasks after the director's import, "Loading..." is never painted, and the ride runs over the fog with the section's loading line: amendment 2 is not in effect. Fix in `hero.ts`, inside the island's 0.3 KB allowance (112 B used): let the hook's `load()` resolve only once the hall is in or has failed, for example `load: () => loadHall().then(() => new Promise<void>((res) => { const tick = () => { const h = ctx.room?.hall; if (life.dead || !h || h.ready || h.failed) res(); else requestAnimationFrame(tick); }; tick(); }))`; or keep the in-flight promise in `hall.ts`'s `load()` (`return loading ??= (async () => { ... })()`), so every caller awaits the same load, a change to section 4's script inside its 0.1 KB allowance.
